# 应用商店与插件后端进程模型

## 一、背景与目标

面板现有插件体系（`internal/plugin/manifest.go`）是**纯前端静态包 + 能力桥**：

- 插件的 `entry` 被强制要求是 `.html`（`manifest.go:166-168`），插件是纯静态资源
- 插件运行在 `sandbox="allow-scripts"` 的 iframe 里，与面板的唯一通道是 `postMessage`（`internal/api/assets/sdk.js:1-11`）
- 插件能做的事完全由 4 项能力决定：`host:list` / `host:exec` / `host:file:read` / `host:file:write`（`manifest.go:19-24`）

这套模型安全，但**能力上限被锁死**：插件不能持有长连接、不能运行自己的业务逻辑、不能有自己的存储。

本次要立项的四类应用，本质是同一件事 —— 在目标服务器上装包、写配置、起服务、失败可回滚：

| 应用 | 真实动作 |
|---|---|
| 中间件一键装（Nginx / MySQL / Redis / PHP / PM2） | 装包 → 生成配置 → 起服务 → 开端口 → 健康检查 |
| 建站 | 装 Web 环境 → 建站点目录 → 写站点配置 → 申请证书 → 建库 |
| WAF | 装模块 → 下发规则 → reload → 规则命中日志 |
| VPN | 装 OpenVPN / WireGuard → 生成证书 → 下发客户端配置 → 起服务 |

这四类都**需要一个能跑自己逻辑的后端**：MySQL 管理器要自己维持连接池并跑 SQL，WAF 要持续消费拦截日志，VPN 要生成并管理证书链。靠 `host:exec` 拼命令拼不出来，也谈不上可回滚。

**本次目标**：给插件体系增加**后端进程**这一种运行时，把应用商店补成完整的接入平台，再把上面四类应用按 P0–P2 立成官方应用。

## 二、已确认的决策（用户拍板）

| 决策 | 选择 | 备注 |
|---|---|---|
| 应用与面板的对接形态 | **插件后端进程模型**（Unix Socket + JSON-RPC） | 对齐 GMSSH 的 DBStudio 路线，换取能力上限 |
| 应用来源 | **官方应用先行**，接口按开放标准设计 | 本阶段不开放第三方上架，但字段与协议不留私有假设 |
| 本轮交付物 | **设计文档 + 接口字段定义** | 不写实现代码 |
| 立项范围 | 建站 / 中间件一键装 / WAF / VPN | 分期见第八章 |

## 三、与 GMSSH 的关系：抄哪一层、补哪一层

GMSSH 唯一开源的插件 DBStudio 给出了完整的进程模型形态：

```
GMSSH 宿主 ──proxy──> Unix Socket (app.sock) ──JSON-RPC──> 插件自己的 Go 后端 ──> MySQL
     └── iframe 挂载插件前端（Vue3 + Naive UI + CodeMirror 6）
```

**抄这一层**：清单声明运行时、宿主拉起并代理进程、插件前端仍是 iframe。这是被验证过能做出 DBStudio 级应用的形态。

**补这一层**：GMSSH 的插件进程与宿主同权限域，插件拿到的是一整套能力而不是收缩后的授权。DBStudio 的后端进程必须常驻在装有面板的机器上，这与它官网首页「不装代理、不占资源」的宣传直接矛盾。

所以本方案在照抄进程模型的同时，补三条 GMSSH 没有的约束（见 5.2）：
1. 插件进程**绝不以 root 启动**，也绝不持有 SSH 凭证
2. 对目标机的一切操作**必须回流面板**，走面板既有的授权与提权链路
3. 能力仍是**逐项授权 + 运行时可收缩**，进程模型不豁免这条

一句话：**进程模型给插件「算力」，不给插件「权限」。**

## 五、运行时模型

### 5.1 清单扩展：`plugin.json` 新增 `runtime` 段

`Manifest`（`internal/plugin/manifest.go:118-127`）增加一个可选字段。**不填即 `static`，现有插件行为零变化。**

```json
{
  "org": "panelssh",
  "name": "mysql-manager",
  "displayName": "MySQL 管理器",
  "version": "1.0.0",
  "entry": "index.html",
  "capabilities": ["host:list", "host:exec", "host:file:read", "host:file:write", "host:tunnel"],
  "runtime": {
    "kind": "process",
    "exec": "bin/mysql-manager",
    "args": ["--socket", "{socket}", "--data", "{dataDir}"],
    "socket": "app.sock",
    "protocol": "jsonrpc-2.0",
    "autoStart": true,
    "idleStopSec": 0,
    "healthPath": "health",
    "stopTimeoutSec": 10
  }
}
```

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `kind` | string | 否 | `static`（默认）/ `process` | 运行时类型；`static` 时其余字段一律忽略 |
| `exec` | string | `kind=process` 时必填 | 包内相对路径，须落在该版本目录内且带可执行位 | 面板直接 `exec`，**不经 `sh -c`**（见下） |
| `args` | []string | 否 | ≤32 项、单项 ≤256 字符 | 支持占位符 `{socket}` `{dataDir}`。原方案列的 `{hostDir}` 已删除：单进程模型下它没有对应路径 —— 插件要访问目标机上的目录，必须回流面板走 `host.exec` / `host.file.*` |
| `socket` | string | 否 | 相对**运行时数据目录**的路径，默认 `app.sock` | 面板负责创建其父目录，并在插件进程建起 socket 后立刻 `chmod 0600`（权限受插件 umask 影响，不收紧就等于同机其他用户能绕开面板直连插件）。**不相对安装包目录**：socket 是运行时产物，落在版本目录里会在升级换版本时被一起替换掉 |
| `protocol` | string | 否 | 目前仅 `jsonrpc-2.0` | 留作将来扩展 |
| `autoStart` | bool | 否 | 默认 `true` | 安装完成后是否自动拉起 |
| `idleStopSec` | int | 否 | 0–86400，`0` 表示常驻 | 无 RPC 调用持续该时长后回收进程 |
| `healthPath` | string | 否 | 默认 `health` | 就绪探测使用的 JSON-RPC 方法名 |
| `stopTimeoutSec` | int | 否 | 1–60，默认 `10` | `SIGTERM` 后等待退出；超时转 `SIGKILL` |

**为什么 `exec` 必须是包内相对路径**：与 `entry` / `icon` 同理，它参与磁盘路径拼接，必须在清单校验阶段就卡死（复用 `normalizeRelativePath`，`manifest.go:203-221`），而不是等落位时再"尽力而为"地过滤。

**为什么不允许经 `sh -c` 启动**：`args` 里的占位符值（socket 路径、数据目录）含有面板算出的绝对路径。走 shell 解释就多了一条注入面；直接 `exec.Command(execPath, args...)` 让参数边界由内核保证。

**为什么要 `idleStopSec`**：这正是 GMSSH 被诟病「常驻占用」的地方。默认常驻是为了响应速度，但必须给用户一个「用完就收」的开关。

### 5.2 进程的权限边界（四条不变量）

这是整个方案的安全地基，实现时任何一条被放宽都必须重新评估。

**不变量 1：进程以面板运行用户启动，绝不以 root 启动。**
面板自身不需要 root（面板通过 SSH 管目标机，`internal/plugin/remote.go:13-18` 已明确「装插件不该变成一次提权操作」）。给插件进程 root 会让整个权限模型崩塌。需要特权的动作一律回流面板，由面板走既有提权链路（`privilege.go`）执行。

**不变量 2：进程不持有任何 SSH 凭证，对目标机的操作必须回流面板。**
插件进程拿不到 `secretbox`、拿不到主机密码、拿不到 `*ssh.Client`。它要操作目标机，只能调面板能力（`host.exec` / `host.pkg` / `host.service` / `host.tunnel`），由面板携带会话身份代为执行。
**这一条是授权模型不破的唯一保证**：一旦插件直连 SSH，`granted` 能力列表就形同虚设。

**不变量 3：进程只能读写自己的数据目录。**
每个插件实例一个目录 `data/plugins-runtime/{org}/{name}/`，内含 `data/`、`logs/`、socket。不提供 chroot —— 以面板用户身份运行时它理论上能读面板的其他文件，这是本阶段接受的残余风险（见第十一章 R4），不作为 P0 阻塞项。

**不变量 4：能力仍逐项授权，进程模型不豁免。**
`capabilities` 的申请 / 授予 / 收缩流程完全复用现有实现（`plugins.go:479-521`）。新增的 3 项能力（5.6）同样走「安装时确认、运行时可收缩、`granted ⊆ capabilities`」。

### 5.3 进程跑在哪台机器

**结论：插件进程只跑在面板所在机器（宿主机），不推送到目标机。**

理由是三条：

1. **不需要往目标机推二进制**。面板是 Go 单二进制，插件进程也是 Go/原生二进制；推过去要匹配目标机架构、glibc 版本、动态库，这会把「装插件」变成「远程部署」，与 `remote.go` 里既有的「用户态落位、不需要 root」原则冲突。
2. **不受目标机环境漂移影响**。目标机升级 glibc 或换发行版会让推过去的二进制直接跑不起来，而跑在面板机上这些问题不存在。
3. **与 DBStudio 的实际形态一致**。GMSSH 的 DBStudio 后端也是跑在装有面板的机器上，通过配置连目标数据库。

目标机侧仍然保留现状：安装包会被推送到 `~/.panelssh/plugins`（`remote.go:51-89`），作为「这台机器上装过什么」的落位记录，插件静态资源也在那里有一份副本。**新增的只是面板机上多一个后端进程。**

**由此确定进程与主机的对应关系**：一个插件**一个进程**（按 `{org}/{name}` 唯一），`hostId` 作为 RPC 调用的上下文参数传递，而不是每台主机起一个进程。

```
POST /api/plugins/{org}/{name}/rpc/{method}
body: { "hostId": 7, "params": { ... } }
```

**为什么不做「每主机一进程」**：dsh 是每主机一个实例，因为 dsh 本体装在那台机器上、每台机器一个独立服务。插件进程跑在面板机上，它本质是一个服务，面向哪台目标机只是参数不同；每主机一进程会在管理 50 台机器时起 50 个进程，纯浪费。

> **待拍板**：若某个应用确实需要按主机隔离的状态（例如同时连两台机器各持一个连接池且互不干扰），可给它加 `runtime.perHost: true` 开关。**P0 不做**，先验证单进程模式是否够用。

### 5.4 双向通信协议

插件与面板之间需要**两个方向**的调用，这是进程模型比纯前端插件复杂的地方：

```
①  面板 → 插件：面板代理插件前端的请求
    浏览器 iframe  --fetch-->  面板  --Unix Socket-->  插件进程
    POST /api/plugins/{org}/{name}/rpc/{method}

②  插件 → 面板：插件申请执行特权能力
    插件进程  --HTTP + X-Plugin-Token-->  面板
    POST /api/plugin-api/{method}
```

**为什么方向 ② 走 HTTP 而不是在同一条 socket 上做反向 RPC**：面板本身就是一个 HTTP 服务器，`requireAuth` / `writeErr` / 能力校验这些都是 HTTP 层已有的东西。在 socket 上再造一套服务端发起的 RPC，等于把能力校验逻辑写两遍，还会引入「面板要维护 socket 上的请求-响应关联」这个纯复杂度。走 HTTP 则所有校验点复用同一处代码。

**为什么 ② 需要令牌而不是直接复用会话 Cookie**：插件进程不是浏览器，没有会话 Cookie。令牌设计如下：

| 项 | 设计 |
|---|---|
| 签发 | 面板拉起进程时生成 32 字节随机令牌，同时写入内存映射与插件目录下 `token` 文件（`0600`） |
| 传递 | 插件读取自己的 `token` 文件，请求时带 `X-Plugin-Token` 头 |
| 校验 | 面板按令牌**只查出 `(org, name)`**，再按该主机上的当前授权逐项判定能力（见下方） |
| 生命周期 | 与进程同生命周期；进程重启即换新令牌；插件卸载立刻失效 |
| 为什么放文件里而不放环境变量 | 环境变量会被 `ps -e` 或 `/proc/<pid>/environ` 泄露给同机其他用户；文件有 `0600` 权限兜底 |

**为什么令牌里不缓存 `granted`**：令牌只回答「你是谁」，「你能做什么」每次回调时按当前授权重新判定。缓存快照会制造一个漏洞窗口 —— 用户撤销了插件的某项权限，而插件手里的令牌还带着撤销前的快照，在进程重启之前一直有效；而撤销授权最需要立刻生效的时刻，恰恰就是它刚被撤销的那一刻。代价是每次回调多一次本地 SQLite 索引查询，与一次跨进程 HTTP 调用相比可以忽略。

**插件能操作哪些主机**：只能操作「装了它」的主机，这台主机的安装记录同时也是授权范围。这条边界沿用自前端能力桥的 `requireOwnHost`（`PluginFrame.vue`：「一个插件之所以有 `host:exec`，是因为管理员在某一台机器上把它装了并为这台机器授了权」），后端进程模型不放宽它。

**① 的转发规则**：

- 面板只做透传，**不解释 `method` 的内容**（插件自定义命名空间，如 `connection.list`、`sql.query`）
- 但**必须校验方案**：`method` 限 `^[a-z][a-z0-9]*(\.[a-z][a-z0-9]*)*$`、长度 ≤64，避免被当作路径或注入
- 请求体上限 32 MiB（与 `maxPluginArchive` 同量级），超时 60 秒
- 插件返回的 JSON-RPC error 原样转成 HTTP 错误体（`writeErr`），不泄露 socket 层细节
- **只有该插件已启用时才转发**，与 `handlePluginAsset` 的启停判定一致（`plugins.go:566-579`）

### 5.5 进程生命周期与孤儿防护

状态机：

```
stopped ──start──> starting ──health ok──> running
                      │                       │
                      └──失败/超时──> failed <┘（崩溃后按退避重启，最多 3 次）

running ──idleStopSec 无调用──> stopping ──> stopped
running ──stop / 禁用 / 卸载──> stopping ──> stopped
```

关键实现点，全部沿用 dsh 已验证的做法：

1. **就绪判定靠主动探测，不靠「进程还活着」**。启动后轮询 RPC `health` 方法，直到返回成功才算 `running`；进程在就绪前退出即为 `failed` —— 与 `dsh/supervisor.go` 的 `readyPattern` + `watch` 同构。
2. **孤儿防护双保险**。本地进程用 `Setpgid` + `Pdeathsig`，终止时 `syscall.Kill(-pid)` 杀整个进程组（`launcher_local.go`）；同时在插件目录写 `pid` 文件，面板启动时扫一遍，`kill -0` 判活并清理上次残留。**只靠 `Pdeathsig` 不够**：面板被 `SIGKILL` 时子进程可能留下。
3. **socket 参数校验前置**。每次转发前确认 socket 文件存在且是 socket（`os.Stat` 的 `ModeSocket`），不存在则先尝试拉起，仍失败返回 `PLUGIN_NOT_RUNNING`（6.3）。
4. **卸载的清理顺序**：先停进程 → 再删远端落位（复用 `handleUninstallPlugin` 的「远端优先」顺序，`plugins.go:417-427`）→ 再删本地记录 → 最后删运行时目录与令牌。停进程必须在最前，否则会留下一个还在跑、但面板已无法管控的进程。
5. **优雅退出**：面板收到退出信号时 `StopAll()`，与现有 `sockets` 统一关闭的做法一致（`server.go:86-87`）。

### 5.6 新增能力项

| `host:pkg` | 在主机上安装软件包 | 经面板提权链路调用发行版包管理器（apt/dnf/yum/apk），走 env 流水线，带快照与补偿 | 中间件一键装、建站、WAF、VPN |
| `host:service` | 启停主机服务 | `systemctl` / `service` 的 enable / start / stop / restart / reload | 中间件一键装、建站、WAF、VPN |
| `host:tunnel` | 建立到主机的隧道 | 面板在插件与目标机的回环端口之间建一条隧道，返回插件可连的本地端口 | MySQL 管理器、Redis 管理器；任何要连目标机仅监听 127.0.0.1 的服务的应用 |

`CapabilityLabel`、`CapabilityOrder`、`knownCapabilities` 三张表同步扩展（`manifest.go:28-44`），前端排版顺序自动跟随。

**为什么 `host:pkg` 不直接给 `host:exec` 提权**：`host:exec` 是「以登录用户身份执行一条命令」，而装包必须提权、必须可回滚、必须防并发。这三件事只有 env 流水线有（`Runner.hostLock` + 快照 + 补偿）。把它做成独立能力，是为了让授权界面上写的是「在主机上安装软件包」这种用户能理解的话，而不是「可以在主机上提权执行任意命令」—— 后者没人敢授权。

**`host:tunnel` 的调用契约**：

```
建立  host.tunnel        { hostId, remoteHost: "127.0.0.1", remotePort: 3306 }
响应                    { tunnelId, localHost: "127.0.0.1", localPort: 41235, expiresAt: null }
关闭  host.tunnel.close  { hostId, tunnelId }
```

- 隧道归插件所有，进程停止或插件卸载时**无条件全部关闭**
- 每次开放记录审计日志（哪个插件连了哪台机器的哪个端口），与现有 `notifySecurity` 的通知机制对齐
- `remoteHost` **只接受 IP 字面量**，且必须是回环或私网地址，不接受域名与外网地址 —— 否则插件能借目标机做代理跳板；不接受域名是为了避免"内网名字被解析到公网"
- 本地监听只开在 `127.0.0.1`：隧道是给同一台机器上的插件进程用的，监听 `0.0.0.0` 会让面板机的网络邻居也借道进目标机
- `tunnelId` 不可枚举（8 字节随机），且关闭时校验归属 —— 只能关自己开的那条
- 单个插件最多同时持有 16 条隧道：不是资源问题，而是"每条隧道都是面板替它开着的一个本机端口"，数量失控后"这个端口是谁开的"会变成查不清的事
- **`close` 也要求带 `hostId`**：这样每条回调都走同一条授权校验链（令牌身份 → 该主机上的安装记录 → 当前授权），不必为关闭动作开一条"只校验隧道归属"的特殊分支
- **`expiresAt` 固定为 `null`**：隧道与插件进程同生命周期，不设独立 TTL。给一个假的到期值只会让插件去做无用的续期；将来若要支持"长期不用的隧道自动回收"，从这一处扩展

**`host:pkg` 与 `host.service` 的调用契约**：

```
host.pkg      { hostId, action: "install" | "remove", packages: ["nginx"] }
host.service  { hostId, action: "enable" | "disable" | "start" | "stop" | "restart" | "reload", unit: "nginx" }
```

- `host.pkg` 走面板既有的环境流水线（`env.Runner.Run`）：装包必须提权、必须可回滚、必须防并发，这三件事只有那条流水线有（`hostLock` + 快照 + 补偿）。单次最多 32 个包 —— 不是性能考虑，而是「一次操作要么成功要么回滚」，包越多失败后留下的半成品状态越难说清，要装一整套依赖就分几次调用
- `host.pkg` 的响应带 `steps`（各步骤的输出与退出码）与 `summary`（含 `opId`，可在面板的「操作记录」里复盘）。流水线本身是流式的、插件回调是同步 HTTP，面板侧用一个收集型 `Events` 把过程攒起来一次交回，插件不必自己实现事件通道
- `host.service` 直接走提权链路（`runEscalated`）：单位名逐字符校验（只允许 systemd 单位名本身的字符集），动作取自白名单。插件拼不出任意命令 —— 这正是不把提权执行交给它的意义
- 两者都是**同步**调用。`host.pkg` 可能跑几分钟，插件侧要设置足够长的客户端超时；面板侧没有 `WriteTimeout`，不会从中间截断

**P2 再评估的能力**（本次不实现）：`host:ssl`（申请与续期证书，建站用）、`host:firewall`（防火墙规则，WAF/VPN 用）。理由是它们各自需要独立的安全评审，不适合与地基同批上线；在 P0/P1 阶段，这两件事由官方应用通过 `host:exec` + 面板既有的 AutoSSL 类配方完成。

### 6.3 错误码

现有错误体只有 `error` 一个字段（`server.go:432-439`），前端只能靠字符串匹配判断类型。新接口在此之上扩展一个**可选** `code`：

```go
type errorBody struct {
    Error string `json:"error"`
    Code  string `json:"code,omitempty"` // 新增，现有接口留空
}
```

**为什么用可选字段而不是新建一套错误结构**：现有全部接口的响应体形状不变，前端判断 `error` 的既有代码零改动；新代码按需读 `code`。新建结构会导致「同一面板两种错误体」。

插件与应用相关错误码：

| code | HTTP | 含义 | 界面应对 |
|---|---|---|---|
| `PLUGIN_NOT_FOUND` | 404 | 插件不存在 | 刷新列表 |
| `PLUGIN_DISABLED` | 403 | 插件已停用 | 提示启用 |
| `PLUGIN_NOT_RUNNING` | 503 | 进程未运行且拉起失败 | 提示查看日志，给「重启」按钮 |
| `PLUGIN_START_FAILED` | 500 | 启动失败（可执行位缺失、架构不匹配） | 展示 `lastError` |
| `PLUGIN_CRASHED` | 500 | 反复崩溃 | 展示日志入口 |
| `CAPABILITY_DENIED` | 403 | 调用了未授予的能力 | 提示去应用中心授权 |
| `CAPABILITY_UNKNOWN` | 400 | 清单申请了未知能力 | 安装失败，提示应用需要更新 |
| `RUNTIME_UNAVAILABLE` | 500 | 面板不支持该运行时（如 `kind` 未知） | 提示更新面板 |
| `ARCH_MISMATCH` | 400 | 包内二进制与面板机架构不符 | 提示应用不支持当前架构 |
| `HOST_ESCALATION_REQUIRED` | 409 | 该应用需要提权但主机未配置 | 引导去主机管理配置提权 |
| `STORE_APP_NOT_FOUND` | 404 | 商店条目不存在 | 刷新商店 |

## 七、四类应用的接入形态（立项范围）

这一节说明每类应用**用什么能力、走什么步骤**，是 P0–P2 分期的依据。

### 7.1 中间件一键装（P0）

- 能力：`host:pkg` + `host:service` + `host:file:write` +（数据库类还要 `host:tunnel`）
- 步骤：env 配方（`catalog.go` 新增 `mysql` / `nginx` / `redis` / `php` / `pm2` 项，写法照 `planNode`）→ 生成配置 → 起服务 → 健康检查
- 插件进程干什么：**只做 UI 与管理逻辑**（连库、列库表、跑 SQL、看慢查询）。装包这件事仍然是面板的 env 流水线在做
- 第一个落地的应用建议是 **MySQL 管理器**：它同时验证「进程 + socket + 隧道 + 包安装」四条链路，是最完整的样板

### 7.2 建站（P1）

- 能力：`host:pkg` + `host:service` + `host:file:write` + `host:exec`
- 形态：**组合应用**。它不重复实现中间件，而是声明依赖（`requires.apps: ["nginx", "mysql", "php"]`），商店在安装时先确保依赖就位
- 额外需要：证书申请（复用面板既有的 AutoSSL 类配方）、站点目录与权限、站点配置模板
- 插件进程干什么：站点列表、站点配置生成、证书状态与续期、访问日志

### 7.3 WAF（P2）

- 能力：`host:pkg` + `host:service` + `host:file:write` + `host:exec`
- 形态：在 Nginx 上装模块（ModSecurity / 自研规则引擎）+ 下发规则 + reload
- 关键约束：**规则下发必须可回滚**。WAF 规则写错会直接切断业务，因此复用 env 的快照-补偿机制，且 reload 前后都要有健康检查
- 插件进程干什么：规则管理、命中日志消费与聚合、误报标注

### 7.4 VPN（P2）

- 能力：`host:pkg` + `host:service` + `host:file:write` + `host:exec`
- 形态：OpenVPN / WireGuard 二选一；证书链生成与管理；客户端配置下发
- 关键约束：**证书私钥不出目标机**。生成在目标机完成，面板只取客户端配置（含客户端私钥，属于必要导出）
- 插件进程干什么：客户端管理、连接状态、流量统计、证书过期提醒

## 八、P0–P2 分期

### P0：地基 + 中间件一键装（打通链路）

| # | 事项 | 验收点 |
|---|---|---|
| 1 | 清单 `runtime` 段 + 校验（`manifest.go`） | 不填 `runtime` 的现有插件行为完全不变（回归） |
| 2 | 运行时管理器（spawn / 就绪探测 / 崩溃重启 / 回收 / 孤儿清理） | 进程被 `kill -9` 后能自动重启；面板强杀后重启面板不留孤儿 |
| 3 | 双向通信：转发接口 ① + 令牌回调 ② | 插件能通过令牌调用 `host.list`，调用未授予能力返回 `CAPABILITY_DENIED` |
| 4 | 新增 3 项能力 + `risk` 分级 | 授权界面按风险升序渲染 |
| 5 | 商店接口：`apps` / `apps/{org}/{name}` / `categories` / `updates` | 分类筛选、搜索、按主机计算的 `installed` 正确 |
| 6 | 运行时接口：`runtime` / `start` / `stop` / `restart` / `logs` | 状态机五态在前端如实呈现 |
| 7 | 安装进度 NDJSON + 前端消费（复用 `EnvRunDialog` 格式） | 失败时 `rolledBack` 正确反映是否已还原 |
| 8 | env 配方：`mysql` | 能装、能起、能卸、失败能回滚 |
| 9 | 官方应用：**MySQL 管理器** | 端到端：装 MySQL → 建隧道 → 插件连上 → 列库表跑 SQL |

**P0 的完成判据**：MySQL 管理器在干净的目标机上从零装起、可用、可卸载、卸载后无残留进程、无残留隧道。

### P1：中间件全家桶 + 建站

| # | 事项 | 验收点 |

| # | 事项 | 验收点 |
|---|---|---|

## 十一、风险与待验证

**实现顺序**（1–4 可独立提交与验证）：

1. 清单 `runtime` 段 + 校验（纯函数，行为不变）
2. 运行时管理器 + 孤儿防护
3. 令牌签发与校验中间件
4. 转发接口 ① + 回调接口 ②
5. 新增 3 项能力 + `risk` 字段（影响现有授权界面，单独提交）
6. 商店接口（只读，先行可用）
7. 运行时接口 + 前端状态呈现
8. 安装进度 NDJSON（影响现有安装流程，单独提交）
9. env 配方 `mysql` + MySQL 管理器应用

**必须在真机上验证的假设**：

- **R1（最关键）**：插件进程的 `Pdeathsig` 在面板被 `SIGKILL` 时是否真的可靠。起一个长跑进程，`kill -9` 面板，`ps` 看它是否还在 —— 这决定 `pid` 文件是「兜底」还是「必需」。dsh 的同类假设（DSH 文档 R1）尚未有真机结论，这里沿用同一条待验证项。
- **R2**：`host:tunnel` 下插件持久连接（MySQL 长连接）在网络抖动后的行为。隧道断开时插件侧应收到连接错误并能重连，而不是静默失效。需要真机拔网验证。
- **R3**：socket 文件在面板用户与插件进程同用户时的权限实际效果。同用户下 `0600` 不能阻止插件读面板的其他文件，这确认了 5.2 不变量 3 的残余风险边界。
- **R4**：`idleStopSec` 回收的判定是否会被「插件自己的后台任务」误判为空闲（例如 WAF 在持续写日志但没有 RPC 调用）。若会误判，需要插件能主动上报「我在忙」。
- **R5（已消解）**：`exec` 二进制的架构兼容。本轮确定**只做 amd64**，因此 P0 不做 `bin/{arch}/` 双架构，`exec` 直接指向包内二进制；将来要支持 arm64 时再引入占位符，届时属于新增而不是返工。

**其他风险**：

- **插件进程与面板同用户运行**意味着它理论上能读面板的 `data/` 下其他内容。这是本阶段接受的残余风险，不引入容器/chroot 的复杂度。**若后续要支持第三方应用（P2），这条必须先解决**（可选方案：`bwrap`/`systemd-run --scope` 隔离）。
- **能力收缩与进程状态不同步**：面板侧不再有这个问题 —— 授权每次回调都重新判定（见 5.4），撤销立即生效。但插件进程自己可能缓存了能力清单，所以**授权变更后仍建议重启插件进程**（让它重新握手拿到新的 `capabilities`）；差别在于这只是让插件的界面显示同步，不再是安全前提。
- **商店条目的资料从哪来**：P0 用本地内置清单（`plugin.Builtins` 的扩展形态）；P2 接远程源时，字段已经按开放标准设计（`publisher` / `stats` / `compat`），不需要改结构。**P0 不引入网络依赖**，保证离线可用。

## 十二、需要你拍板的设计点

以下是我在本方案中做出的取舍，你尚未表态。**P0 开工前需要确认**，否则后续会返工：

| # | 设计点 | 我的选择 | 另一条路 |
|---|---|---|---|
| 1 | 进程位置 | 只跑在面板机 | 每台目标机一份（像 dsh），代价是要推二进制、匹配架构 |
| 2 | 进程与主机的关系 | 一个插件一个进程，`hostId` 作参数 | 每主机一进程，代价是 N 台机器 N 个进程 |
| 3 | 插件→面板的通道 | HTTP + `X-Plugin-Token` | socket 上的反向 JSON-RPC，代价是能力校验写两遍 |
| 4 | `host:pkg` 是否独立成能力 | 独立（走 env 流水线，可回滚） | 并入 `host:exec`，代价是无法对用户解释、无法单独授权 |
| 5 | 双架构二进制 | 包内 `bin/{arch}/` + 清单占位符 | 只支持面板机架构，代价是 arm64 NAS 用户装不了 |
| 6 | `errorBody` 扩展 | 加可选 `code` 字段 | 新建错误结构，代价是同一面板两种错误体 |
| 7 | 第三方开放时机 | P2，且开放前必须先解决进程隔离 | P0 即开放，代价是安全评审来不及 |
