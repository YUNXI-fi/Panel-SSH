# 窗口多开 与 文件管理「更多」增强

## 背景

两件事：

1. **同一个应用无法同时开两个窗口**。`launch()`（[Desktop.vue](file:///media/yunxi/FE73-D3B5/Panel%20SSH/web/src/desktop/Desktop.vue#L181-L193)）发现已有同应用窗口就只聚焦，用户没法同时盯两台机器的监控。
2. **文件管理行操作太少**。`更多` 菜单（[FileManager.vue](file:///media/yunxi/FE73-D3B5/Panel%20SSH/web/src/windows/FileManager.vue#L459-L469)）只有 打开/下载、在线编辑、重命名、删除…，缺日常运维最常用的复制、移动、改权限、压缩解压。

已与用户确认的边界：

* 多开**只给带主机选择的 7 个应用**（终端、文件、监控、进程、网络、存储、环境）；主机管理、批量执行、AI 助手、应用中心仍保持「回到已有窗口」——它们没有主机这个区分维度，多开只会堆一样的窗口。

* 压缩解压**同时支持 tar.gz 与 zip**（zip 依赖目标机的 `unzip`，缺失时由远端报错透传）。

* 新增的四类操作（chmod / 复制 / 移动 / 压缩解压）全部落在**行菜单**上，靠已有勾选状态扩展批量能力。

## 一、窗口多开

### 1.1 前提：窗口标题必须能区分主机

不改这个，两个「资源监控」窗口标题相同、竖栏任务项也是同一个图标，多开等于白开。所以要先让窗口标题能带主机名。

* [useWindowManager.ts](file:///media/yunxi/FE73-D3B5/Panel%20SSH/web/src/desktop/useWindowManager.ts)：`AppWindow` 增加 `subtitle: string`（默认 `''`）；`WindowManager` 增加 `setSubtitle(id, text)`；同文件导出 inject key `WindowSubtitleKey`。

* [WindowFrame.vue](file:///media/yunxi/FE73-D3B5/Panel%20SSH/web/src/desktop/WindowFrame.vue)：标题渲染改为「有 subtitle 时显示 `标题 · 副标题`」。

* **机制改动点**：WindowFrame 目前是 `<slot />` 容器，而 Vue 中 slot 内容的 inject 链走 slot 的**定义方**（Desktop），WindowFrame 的 `provide` 不会被内容组件看到。因此把 WindowFrame 改为**自己渲染内容组件**：新增 `comp`、`data` 两个 prop，模板里 `<component :is="comp" v-bind="data" />` 取代 `<slot />`。这样内容组件的父实例是 WindowFrame，`provide(WindowSubtitleKey, (text) => wm.setSubtitle(props.win.id, text))` 才生效，也不必为窗口 id 再加一层包装组件。

* [HostPicker.vue](file:///media/yunxi/FE73-D3B5/Panel%20SSH/web/src/components/HostPicker.vue)：`inject(WindowSubtitleKey)`，`watch(hostName)` 时把主机名写上去。inject 不到时静默跳过（该组件也被窗口外的地方复用）。

* [Desktop.vue](file:///media/yunxi/FE73-D3B5/Panel%20SSH/web/src/desktop/Desktop.vue)：`<WindowFrame>` 由 slot 写法改为传 `:comp="resolve(win.appKey)"` / `:data="win.props"`；竖栏任务项的 `:title` 与 `:aria-label` 用同一套「标题 · 副标题」拼接（抽一个小函数，两处共用）。

从「主机管理」行内点开的窗口已经是 `终端 - ${host.name}`，不受影响。

### 1.2 launch 分组

* `AppEntry` 增加 `multi?: boolean`；终端、文件、监控、进程、网络、存储、环境这 7 项置 `true`。

* `launch()` 开头加分支：`app.multi` 为真时直接 `wm.open(...)`，其余保持现有的「找可见窗口 → 还原并聚焦」逻辑。

## 二、后端新增文件接口

统一风格复用现有工具：`s.pathID` / `decodeJSONBody` / `requireAbsPath` / `openSFTP` / `writeJSON` / `writeErr` / `writeHostError`（见 [files.go](file:///media/yunxi/FE73-D3B5/Panel%20SSH/internal/api/files.go#L486-L563) 的既有 handler 结构）。

路由注册在 [server.go](file:///media/yunxi/FE73-D3B5/Panel%20SSH/internal/api/server.go#L197-L205) 的文件管理分组内：

| 路由                     | 用途                 | 实现路径                                                                                                                           |
| ---------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| `POST /files/chmod`    | 改权限                | 直接复用已封装的 `sftpGuard.Chmod`（[sftp.go](file:///media/yunxi/FE73-D3B5/Panel%20SSH/internal/api/sftp.go#L149-L152)）；权限不足再走 root 重做 |
| `POST /files/copy`     | 复制到目标目录            | 登录用户 `cp -a --` 优先，失败且是权限问题再用 root 重做                                                                                          |
| `POST /files/move`     | 移动到目标目录            | 先试 SFTP `Rename`（同文件系统最快路径），被跨文件系统或权限拒绝时退回 `mv -f --`                                                                          |
| `POST /files/compress` | 压缩为 .tar.gz / .zip，过程回传进度 | `tar czf -v` 或 `zip -r`，输出落在源目录同级，同名先报冲突；响应是 NDJSON 进度流 |
| `POST /files/extract`  | 解压，过程回传进度           | 按扩展名选 `tar xzf` / `unzip -o`，解压到所在目录；zip 先探测目标机有没有 `unzip`，缺了直接提示安装 |

### 压缩 / 解压的进度回传

这两个接口的响应不再是"一次性 JSON"，而是 `application/x-ndjson` 的进度流（`runArchiveStream`）：

* 脚本先输出一行 `PANELSSH_TOTAL <n>` 给出总条目数，之后每输出一行即代表处理完一项；`archiveProgress` 数行、按 150ms 节流下发 `{"type":"progress","total":n,"done":m}`。
* 之所以按**条目数**而不是字节数计时：压缩包大小与源大小不是线性的，而 `tar -v` / `zip` 的逐条输出天然就是一份计数器 —— 代价是命令不能再用 `-q`（zip）/ 必须加 `-v`（tar）。
* 帧类型：`prepare`（正在统计条目数）/ `progress` / `escalating`（权限不足，改以 root 重做）/ `done` / `error`。
* **契约：一旦开始下发就恒为 200**，此后的失败放在 `error` 帧里；只有流开始前的校验（鉴权、同名冲突等）才是非 2xx，那时仍是普通 JSON 错误。
* 提权那一段走既有的一次性执行通道，拿不到逐条输出，因此进度会退回"不确定"态（`escalating` 帧 + 条纹动画），而不是卡在某个数字上。
* 流式执行由 `execOnHostStream` 提供（`execOnHost` 即其 `onLine == nil` 的封装），口径与同步版完全一致，否则"要不要提权重试"的判据会在两条路径上分叉。
* 压缩包名不能以 `-` 开头：Info-ZIP 的 `zip` **不认 `--` 选项分隔符**（会报 `can't use -- before archive name`），名字只能紧跟在选项后。

### 关键约束：不能直接以 root 执行

[files\_privilege.go](file:///media/yunxi/FE73-D3B5/Panel%20SSH/internal/api/files_privilege.go#L15-L26) 已经写明了原因：无脑提权会让用户自己目录里新建的文件变成 root 属主，之后他自己都改不了。而现有的 `runEscalatedFileStep` 是**直接以 root 执行**的，所以这五个接口不能直接调它。

新增一个「两步执行」辅助（放在 files\_privilege.go，紧邻 `runEscalatedFileStep`）：

1. 先用 `execOnHost` 以**登录用户**跑命令；
2. 退出码为 0 → 成功；
3. stderr 命中权限失败文案 → 用 `runEscalatedFileStep` 以 root 重做；
4. 其它失败 → 原样透出 stderr，不重做（磁盘满、命令不存在，提权也救不回来）。

路径拼接一律走已有的 `shellQuotePath`（同文件的命令注入测试 `files_privilege_test.go` 覆盖了它）。

## 六、文件属性与文件哈希

后续补的两件事，仍然落在文件管理窗口里：

1. **属性**：弹窗展示一个条目的完整元数据（属主、属组、三类时间戳、inode、硬链接数、符号链接目标、磁盘占用），
   并允许就地修改**权限 / 属主 / 属组 / 修改时间 / 访问时间** —— 这些原先只能去终端敲 `chmod` / `chown` / `touch`。
2. **哈希**：对文件或目录计算摘要，支持 SHA-256 / SHA-512 / SHA-1 / MD5 / BLAKE3，目录递归展开，
   结果以表格呈现并可复制 / 导出成校验清单。

两条硬约束决定了实现形态：

* **算法命令按目标机能力分流**：`sha256sum` 等由 coreutils / busybox 提供，绝大多数目标机都有，让目标机算最省面板带宽；
  `b3sum` 基本不存在，这种情况由面板自己读文件算（SHA 系列也走同一套兜底，保证五种算法行为一致）。
* **提权沿用既有判据**：改属主、改系统文件的时间戳都需要 root，但绝不能无条件提权 ——
  一律走 `runFileStep`（先按登录用户做，被权限拒绝再提权），避免用户自己的文件被改成 root 属主。

### 6.1 属性读取 —— 新文件 `internal/api/files_attr.go`

路由 `GET /api/hosts/{id}/file/attr?path=...`（只读，沿用 `file/text`、`file/download` 的单文件 GET 约定）。

两个数据来源合起来才够用：

* **SFTP `Lstat` + `ReadLink`**（走已有的 `openSFTP`）：存在性、类型、size、mode、UID/GID、mtime、atime、符号链接目标。
  pkg/sftp 的 `FileStat` 已含 `UID`/`GID`/`Atime`，经 `info.Sys().(*sftp.FileStat)` 取出，无需额外请求。
* **一条 `stat` 命令**补齐 SFTP 给不出的字段：属主名、属组名、ctime、硬链接数、inode、占用块数。

```
stat -c '%U<TAB>%G<TAB>%Z<TAB>%h<TAB>%i<TAB>%b' -- '<path>'
```

* 字段间用真实制表符分隔而不是解析默认输出：默认输出是为人排版的，列宽随内容浮动，文件名带空格时无法可靠切分；
  而制表符不可能出现在用户名或组名里，切分因此是确定的。
* 不加 `-L`，与 SFTP 的 `Lstat` 同口径 —— 属性面板展示的是链接自己，不是它指向的文件。
* `%b` 是 512 字节块数，乘 512 得到磁盘占用。
* **这条命令失败不报错**：`stat` 缺失或被拒时这几项留空 / 0，前端显示 `—`。
  属性面板的主干信息来自 SFTP，不该因为一条可选命令而整个打不开。真正的"文件不存在"由 SFTP 那步给出准确报错。

返回体 `attrResponse` 的字段与前端 `FileAttr` 一一对应：`path` `name` `isDir` `isLink` `linkTarget`
`size` `blocks` `mode`（`-rw-r--r--`）`modeOctal`（`755` / `4755`，可编辑区回填用）
`uid` `gid` `owner` `group` `atime` `mtime` `ctime` `nlink` `inode`。

* 时间统一用 `time.Time`（与 `fileEntry.ModTime` 同口径），前端拿到的是绝对时刻；`ctime` 为零值表示没取到。
* `octalPerm` 保住 setuid/setgid/sticky 那一位：少了它，用户一保存就把 setuid 悄悄抹掉了。

### 6.2 属性修改 —— 同 `files_attr.go`

| 路由 | 入参 | 实现 |
| --- | --- | --- |
| `POST /api/hosts/{id}/files/chown` | `{paths, owner, group}` | `chown -h '<owner>:<group>' -- '<p>'` |
| `POST /api/hosts/{id}/files/touch` | `{paths, mtime, atime}`（epoch 秒，0 = 不改） | `TZ=UTC touch -h -m/-a -t <YYYYMMDDhhmm.ss> -- '<p>'` |

* **权限不动**：复用已有的 `POST /files/chmod` 与 `handleChmod`，不重复实现一套。
* `chown` 的 spec 由服务端拼：两个都给是 `owner:group`，只给属主是 `owner`，只给组是 `:group`。
  owner/group 只做最松的校验（非空、不含 `:`、不含控制字符与空白、长度上限）—— 注入由 `shellQuotePath` 兜住，不做多余的白名单。
* `touch` 用 POSIX 的 `-t` 而不是 GNU 的 `-d @epoch`：`-t` 在 GNU / busybox / BSD 上写法一致，`@` 前缀是 GNU 扩展。
  时间在 Go 侧换成 UTC 分量，配 `TZ=UTC` 前缀，两边时区就无关了；`-a` 与 `-m` 互不覆盖，所以分别执行。
* 脚本开头必须 `set -e`：默认 `sh` 会跑完剩下的命令并以最后一条的退出码收场，
  于是"第一条路径就失败了"会被后面成功的命令掩盖成成功。
* 三个请求是**独立的**，前端只提交真正被改动过的字段 —— 打开属性面板本身绝不能改任何东西。

### 6.3 哈希 —— 新文件 `internal/api/files_hash.go`

路由 `POST /api/hosts/{id}/files/hash`，入参 `{paths: []string, algo: string}`。

沿用压缩 / 解压那套 **NDJSON 逐帧**契约（见「压缩 / 解压的进度回传」）：一旦开始下发就恒为 200，
真正的失败放 `error` 帧。事件结构：

```
{type:'prepare'}                              正在扫描 / 统计
{type:'progress', total, done}                进度（复用 archiveTotalMarker 做分母）
{type:'result', path, size, hash, error}      一个文件的结论，path 是相对选中根的路径
{type:'escalating'}                           权限不足，改以 root 重做
{type:'done', total, done}  /  {type:'error', message}
```

* `size` 是**指针**：走目标机命令时 `sha256sum` 不输出大小，指针用来区分"确实是 0 字节"与"这条路拿不到大小"，
  界面据此显示 `—` 而不是一个假的 0。
* 单行失败放在该行 `result` 的 `error` 里继续，整批失败才是 `error` 帧。

**算法与命令映射**：`sha256→sha256sum`、`sha512→sha512sum`、`sha1→sha1sum`、`md5→md5sum`、`blake3→b3sum`。

**分流一：目标机有该命令** —— 脚本与压缩那边同构，复用既有的 `archiveScript` / `archiveTotalMarker` / `missingCommand`：

```
find -H <roots...> -type f -exec <hashCmd> {} +
```

* `find <单个文件>` 本身就只输出该文件，文件与目录走同一条脚本，不必分支。
* 用 `-H` 而不是 `-L`：只跟随命令行上给出的链接（用户选中一个指向目录的链接时，意图显然是算目标目录），
  树内部的链接不跟随 —— 既与面板侧遍历的口径一致，也不会被自指的链接带进死循环。
* 逐行输出 `<hex>  <绝对路径>`，按算法固定的 hex 长度（32/40/64/64/128）切分，分隔符接受 `' '` 与 `'*'`
  （coreutils 在二进制模式下写"空格加星号"）—— 比"找第一个双空格"稳，路径里出现连续空格也不会错位。
* 摘要位上的**十六进制校验不能省**：`sha256sum` 读不了某个文件时会把
  `sha256sum: /path: Permission denied` 写在 stderr 上，而两条流在这里是混在一起的，
  不校验就会把错误信息的前 64 个字符当成一个摘要。
* Go 侧把绝对路径换算成相对选中根的路径（根是文件时取 basename，根是目录时剥掉前缀，根是 `/` 时不会拼出 `//`）。
  这个相对路径正是 `sha256sum -c` 认得的形式，导出的清单可以拿到目标机上原样校验。
* 收场判据是 `res.ExitCode == 0 || 已出结果数 > 0`：个别文件读不了不该让整批作废，
  差额由 `done` 帧的 total/done 如实呈现。**一条结果都没有**时才判断是不是权限问题，是就改用 root 重做一遍。
* 提权通道拿不到逐条输出，只能整段跑完再解析并逐行重放 —— 结果一样完整，只是等待期间进度退回不确定态。
  重放不会产生重复结果帧：能走到那里说明一条结果都没出过。
* 探测命令失败（连不上等）**不能断言"目标机没装"**，那种情况直接走面板侧 —— 面板侧不依赖目标机装任何东西。

**分流二：目标机没有该命令（BLAKE3 的常态）** —— 面板侧读文件算：

* 五种算法都实现，`crypto/sha256`、`crypto/sha512`、`crypto/sha1`、`crypto/md5` 来自标准库；
  BLAKE3 引入 `lukechampine.com/blake3`（v1.4.1，32 字节输出，与 `b3sum` 默认口径一致）。
* 遍历不跟随目录内的符号链接（与 `find` 不带 `-L` 同口径，也防自指死循环），只收 `Mode().IsRegular()`
  （管道、设备、socket 读起来会阻塞或永远读不完）；子目录读不了就跳过，不让整批失败。
* 先遍历出文件清单并发出 `total`，再逐个 `client.Open` + `io.Copy(hasher, f)` 流式读 —— 用固定缓冲区，
  不把整文件载入内存，几个 GB 的文件才不会把面板拖垮。
* 这条路走 SFTP，用的是登录用户权限（文件管理模块不支持提权，见 `openSFTP` 的说明），
  因此读不了的文件只能如实标在那一行上。
* 进度帧按既有的 `archiveProgressInterval`（150ms）节流；回调来自两条拷贝协程，计数与响应写入共用一把锁。

## 七、文件操作并入任务记录

### 7.1 问题与取舍

竖栏「任务记录」只显示批量执行的历史：哈希算完、压缩解压完、上传下载完，窗口里什么都没有 ——
而用户刚把这几件事做完，正是最想回看的时候。

取舍是**不新建"文件任务"表，直接复用 `tasks` / `task_results`**：

* 任务记录窗口、通知中心的跳转、LED 与计数聚合全部零改动，只需要按 `kind` 换措辞。
* 两类任务在"哪台机器、成没成、花了多久"上语义完全一致，差别只在"处理了多少个对象"——
  批量执行是 N 台主机，文件操作是 N 个文件。
* 代价是 `tasks` 需要冗余一列 `host_name`。文件操作没有"逐台结果"，列表里那行 `#id · 时间 · N 台`
  会变成"哪台机器都不知道"，所以发起时把主机名抄一份存下来，避免列表侧为了显示主机名再 JOIN 主机表
  （主机可能已被改名或删除）。

### 7.2 表结构

`internal/store/store.go` 里 `tasks` 增加三列，新增 `task_items` 存明细：

```sql
-- tasks 追加（走 ensureColumn，老库自动升级）
kind       TEXT NOT NULL DEFAULT 'batch'   -- batch / hash / compress / extract / upload / download
host_name  TEXT NOT NULL DEFAULT ''        -- 文件任务冗余的主机名
algo       TEXT NOT NULL DEFAULT ''        -- 哈希算法，仅 hash 任务有值

CREATE TABLE IF NOT EXISTS task_items (
    id      INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id INTEGER NOT NULL,
    path    TEXT    NOT NULL,
    size    INTEGER NOT NULL DEFAULT -1,   -- -1 表示拿不到大小，与 0 字节不是一回事
    hash    TEXT    NOT NULL DEFAULT '',
    error   TEXT    NOT NULL DEFAULT ''
);
CREATE INDEX IF NOT EXISTS idx_task_items_task ON task_items(task_id);
```

迁移沿用既有 `ensureColumn`（先 `PRAGMA table_info` 判断再 `ALTER`，不靠匹配驱动的错误文案）。
老记录升级后 `kind` 为 `batch`，批量执行的既有行为一字未变。

新增 `CreateFileTask`（摘要写进 `command` 列，它是这一行在列表里的标题）、`AddTaskItems`（单事务 + Prepare 批量插入）、
`FinishFileTask`；`ListTasks` / `GetTask` 相应多选这几列，`TaskDetail` 追加 `items`。
批量任务的 `items` 是**非 nil 空数组**而不是 nil —— 前端据此无脑渲染，不必再判一次空。

### 7.3 后端：新文件 `internal/api/files_task.go`

一个 `fileTask` 收口"登记 → 攒明细 → 落状态"的全过程，各操作点只调四个方法：

* `beginFileTask(hostID, kind, summary, algo)`：登记任务。**落库失败只记一条 warn 日志，绝不中断操作** ——
  记录不上不该让用户传不了文件。此时 `id = 0`，后续落库整体跳过。
* `addItem(path, size, hash, errText)`：逐条累积，内部同时记总数与失败数。
  * **哈希逐条入库**：清单本身就是这次操作的产物，任务中途被打断时，已经算完的那部分必须留下来。
  * **压缩 / 解压攒在内存里，结束时一次性写**：逐条写库会让几万次 INSERT 拖慢传输本身。
    上限 `maxFileTaskItems = 50000`，超出部分只计数不存储，并在结果的备注里如实写明"明细仅保留前 N 条"。
* `setTotal(n)`：压缩 / 解压的提权通道拿不到逐条输出（整段跑完再解析），用统计阶段的分母兜底；已有逐条计数时不用。
* `finish(errText)` / `abort()`：`settle` 里用 `settled` 标志保证**只落一次** ——
  defer、错误分支、客户端断开三条路都可能走到这里。状态映射到既有三态：

| 情形 | status | 前端表现 |
| --- | --- | --- |
| 出错（连接断、命令跑不起来） | `error` | 红 LED，「失败」 |
| 跑完了但有个别文件没处理成 | `failed` | 黄 LED，「部分失败」 |
| 跑完了且全部成功 | `success` | 绿 LED，「成功」 |
| 客户端中途断开 | `interrupted` | 黄 LED，「已中断」 |

写入顺序是**先写明细再写状态**，否则会出现"已完成但清单为空"的瞬间。
量词按 kind 区分（哈希 / 上传 / 下载说"个文件"，压缩 / 解压说"个条目"），能说清的事不要留给用户猜。

### 7.4 四个接入点

`internal/api/files.go`：

* **下载**：`io.Copy` 前后各一行 —— 拷贝出错记 `addItem(..., copyErr)` 后 `abort()`，成功记实际字节数后 `finish("")`。
* **上传**：guard 之后登记，用 `failure` 变量 + defer 统一收场（`r.Context().Err() != nil` 判客户端断开）。
  散落的 8 条出错路径各补一行 `failure = "..."`，沿用原有的 `writeErr` 措辞，**不新增用户-facing 的错误文案**。
* **压缩 / 解压**：`runArchiveStream` 的签名从两处字符串收敛成 `archiveOp{what, kind, target, dest}`；
  原来 4 处 `notify(error)` 换成局部函数 `fail(msg)`，它同时负责记 `failure` 与推错误帧 —— 这正是"收场时能拿到原因"的来源。
  进度回调里的非标记行（即逐条文件名）追加 `addItem(archiveItemPath(text), -1, "", "")`；
  `archiveItemPath` 剥掉 `adding:` / `inflating:` / `extracting:` / `creating:` 前缀与 zip 的 `(deflated 65%)` 尾巴。

`internal/api/files_hash.go`：`line()` 里记"目标机命令"那条路的逐行结果（它不输出大小，记 -1），
`result(ev)` 里记面板侧那条路的结果；`fail(message)` 额外把错误留在 `errMsg` 上，供 defer 读取。

## 八、哈希弹窗：先列清单，再看状态

### 8.1 问题

哈希弹窗打开时是一片空白加一句提示，行只在开始计算之后一条条长出来 ——
用户是在为一个自己没看清范围的操作等进度：到底要算多少文件、都算了哪些，动手前无从知道。

### 8.2 清单从哪来：新接口 `POST /files/scan`

新增 `internal/api/files_scan.go`，与计算**分成两个请求**，因为二者的时机不同：
打开弹窗要看清范围，而计算要等用户确认算法之后才动手。清单与算法无关，所以换算法不必重扫。

* 遍历交给目标机的 `find -H <roots> -type f`：一次连接、一次遍历，比面板侧 SFTP 逐层列目录快得多。
  路径用 `relativeUnder` 换算成**与哈希结果帧同口径**的相对路径 —— 界面靠这个把"等待中"的行
  与随后到来的结果一一对上。
* 逐批下发（`scanBatchSize = 200`）：逐条下发会让几万文件的目录推几万帧，界面光处理帧就卡住；
  整批一帧则首批要等到扫完才出现，用户看不到"它动起来了"。`scanBatches` 是切批的纯函数，有单测。
* **一条也没列出来**才报 error 帧（权限所限时 find 会边报错边继续输出，那与哈希计算的取舍一致：
  少几个文件好过整批作废）。报错不阻断：用户仍可以直接点「开始计算」，那条路自带提权兜底。
* 根路径的存在性校验与分类抽成 `classifyHashRoots`，`handleHash` 与 `handleFileScan` 共用 ——
  同一个 `Stat`（跟随链接，与 `find -H` 同口径）既标出"是不是目录"，又顺手完成校验。

### 8.3 表格：文件 / 大小 / 哈希值 / 状态

* **哈希值**列写作 `SHA-256: d7ecfc2a…`（半角冒号）。算法名单独包一层且 `user-select: none` ——
  摘要的用途是粘到别处比对，`user-select: all` 一键选中时应当只拿到纯摘要。
* **状态**列：等待中 / 计算中 / 已完成 / 失败 / 未完成。
  * `missed`（未完成）与 `failed`（失败）必须分开：后者是"它报错了"，前者是"没算出结果、
    也没有任何报错留下来"（通常是读不动）。合成一个会让用户以为背后藏着一句被丢掉的错误。
  * 结果按遍历顺序回来，所以"下一条还没算的"就是正在算的那一个 —— `hashCursor` 只往前推，
    整体 O(n)；那一行顺手带上整批进度（`计算中 3/12`）。
  * 收场（done / error / 连接中断）时把仍停在等待中 / 计算中的行记成未完成，
    不让它们永远停在"等待中"。
  * 结果帧的路径在清单里找不到时补一行（扫描失败，或扫描之后目录里又多了文件）——
    总比让这条结果凭空消失好。
* **虚拟滚动**：预列清单意味着几万行会立刻进表格，全渲染会把页面卡死。开启 `virtual-scroll` 后
  只渲染可视区，代价是**每一列都必须给固定宽度**（`minWidth` 的弹性列在虚拟滚动下不成立）。
* 空状态只剩三种过渡态：正在列出 / 列出失败（并提示可以直接开始计算）/ 这个范围里没有文件。
* 扫描用 `AbortController`：关掉弹窗与窗口卸载时显式中止。流式请求不会因为弹窗关掉就自己停，
  否则目标机还在为一个已经关掉的弹窗遍历大目录。
* 清单在手时点「重新计算」只清值、不动行 —— 重算不该让表格整片消失再长回来。
* 导出清单的过滤条件补上"必须有摘要"：清单里的等待中 / 未完成行没有摘要，
  混进去会拼出只有路径的垃圾行，`sha256sum -c` 读到这里就报错。

### 8.4 验证

单测 `internal/api/files_scan_test.go`：`scanBatches` 的空输入、恰好一批、多出一条、整批切完，
以及批大小非法时退回默认值 —— 切批边界错了不会让任何一处报错，只会让界面上的清单一少一批。

手工验收：在文件管理里对一个目录点「计算哈希」，弹窗打开即列出该目录下所有文件（状态"等待中"）——
点「开始计算」后逐行变成"计算中 N/M → 已完成"，哈希值列显示 `算法: 摘要`；换算法不必重扫；
关掉弹窗再打开会重新扫描。

### 8.5 实机暴露的两个问题

**一、sshd 的登录提示被当成了一个文件。** 目标机上登录用户的家目录不存在时（账号创建时没带家目录、
家目录被删、或它所在的盘没挂载），sshd 在起 shell 之前会往会话里打一行
`Could not chdir to home directory /home/admin: No such file or directory`。它排在命令输出的最前面，
而扫描**按"一行一个文件"解析**，于是清单里出现了一个名字是这句话的"文件"，工具栏还把它算进总数。

修在两处，一处治标一处治本：

* `isSessionNoise`（`exec.go`）：在会话输出的出口滤掉这句话。**所有流式消费方都要靠"一行等于命令的
  一行输出"这个前提**，而 sshd 的提示打破的正是它 —— 压缩/解压的逐条进度同样会把这句话算成一条
  条目（分母来自 `find | wc -l`，不含它，于是进度多出一条并被钳在 100%）。滤在这一层，两个功能一起好。
* 扫描侧再加一道领域内的守卫：**只接受落在某个选中根之下的行**。find 只会输出命令行给出的路径
  或它下面的路径，所以"不归属任何根"就等于"不是文件" —— find 自己的报错（`find: '/x': Permission
  denied`）也一并挡掉，不必逐个去认它的措辞。

注意：写进库里的**原始输出**（`res.Stderr`，用于判断"是不是权限不足"）保持原样，滤的只是交给
流式消费方的那一份。

**二、计算全部"未完成"，真正的原因是超时。** 任务记录里留着实据：

```
kind=hash algo=md5 total=0 err="计算哈希失败：执行失败：执行超时"   dur=120045ms
```

120045 ms 正好是 `fileEscalateTimeout`（2 分钟）。那个数是给"拷贝一个文件"定的，而**哈希要把每个
字节都读一遍，耗时正比于数据总量** —— 一个几十 GB 的数据集在机械盘上远超 2 分钟，用户拿到的是
"一个结果都没有"加一句执行超时。改为专属的 `hashTimeout = 30 分钟`，普通与提权两条路都用它。

同时把 `fileScanTimeout` 从 60 秒提到 5 分钟：它只列路径，正常几秒就完；但挂载在网络存储上、
或机械盘上的大目录一旦超时，表现就是"清单列不出来"——那正是这个功能唯一要做的事。

**进度为什么长时间停在 `0/N`（实测澄清）**：起初怀疑 `find -exec md5sum {} +` 的输出被管道整块缓冲，
用三个 120 MB 文件实测否掉了这个猜测 —— 三行摘要分别落在 .794 / 1.105 / 1.314 秒，**算完一个就吐一行**。

真实原因是"一个文件读完才有一行结果"：目标机是**一个摘要进程**按列表顺序逐个读文件，摘要工具不会
报告"这个文件读到 40%"，所以一个几 GB 的文件会让"已完成数"长时间停在 0。实机上的两次记录都是 0 条：

| 任务 | 时长 | 目标机回传的结果 |
| --- | --- | --- |
| 2 分钟超时那版 | 120.0 s（被掐断） | 0 条 |
| 放宽到 30 分钟那版 | 15.7 min（面板重启打断） | 0 条 |

因此"运行中"那一行的状态里直接列出三样东西：整批进度（`计算中 0/N`）、**正在算的文件名**（超长省略、
完整路径在 `title`）、以及**已用时长**（每秒跳）。文件名必须直接显示而不是只放进 `title` ——
"算的是哪一个"是要一眼看到的；没有它和计时，界面看起来就和卡死一样，用户分不出"在慢慢读"和"早就断了"。
这也正是用户提出"为什么不是排队计算"的原因。

**顺带明确一处表意**：列表里的"等待中 / 计算中 / 已完成"是**对结果到达顺序的呈现**，不是面板在做
逐个文件的调度（面板只把整批交给目标机的一条命令）。"计算中 `0/N`"里的 0 是**已算完的文件数**，
不是"正在算第几个"。

## 九、哈希的字节级进度（百分比）

### 9.1 为什么必须有

上两节的结论是"一个文件读完才有结果"，那么一个几十 GB 的文件就会让界面在 `0/N` 上停十几分钟。
只显示"已用时长"能证明它没死，但用户要的是**百分比**。摘要工具不提供这个信息，只能在脚本层补。

### 9.2 目标机侧：包一层 sh 观察读位置

`hashScript` 不再把文件直接交给摘要工具，而是 `find … -exec sh -c <每文件脚本> panelssh {} +`
（`hashPerFileScript`）。对每个文件：

* 先打印 `PANELSSH_HASH_ITEM <字节数> <路径>` —— 宣告"开始读哪个文件"，界面的百分比要有分母。
* 摘要工具照旧**自己读文件、自己输出摘要行**（格式与解析侧完全没动）。
* 同时起一个每秒轮询的观察者，读 `/proc/<摘要进程 pid>/fdinfo/*` 里最大的 `pos:`，
  打印 `PANELSSH_HASH_PROGRESS <已读> <总字节>`。

**关键取舍：不去碰读取本身。** 另一种做法是"分块读、把块喂给摘要工具"（`dd bs=… skip=… | md5sum`），
但那样一旦读少/读错一个字节，报出去的就是**错摘要** —— 而摘要正是用户拿去核对文件的凭据。
观察文件偏移则完全没有这个风险：读与算还是同一个进程、同一次顺序读，进度只是旁观。

* 小文件（不超过 `hashProgressMinBytes = 32 MiB`）走**原来那条路径**，不多起任何进程：一个几万个小
  文件的目录不该为进度多付几千次 fork。
* 拿不到 `/proc`（受限容器）时进度行整行省掉，界面自动退回"只有已用时长"，不会显示假的 0%。
* 路径解析只按**第一个空格**切分：字节数一定是纯数字，右边整段都是路径（文件名里可以有空格）。
* 摘要行的格式没变，所以 `parseHashLine`、`relativeUnder`、清单导出（`sha256sum -c` 认得的形式）
  一行都不用改。

### 9.3 面板侧那条路

`hashViaPanel` 本来就要把字节读过来，所以顺手就报：`hashOneFile` 从 `io.Copy` 改成固定 1 MiB 的
逐块读（内存用量同一量级），每块回调一次 `p.bytes(done, total)`；节流沿用 `archiveProgressInterval`。

### 9.4 帧与界面

`hashEvent` 增加两帧：`item`（`path` + `size`）与 `bytes`（`path` + `bytes` + `bytesTotal`）。
`Bytes/BytesTotal` 特意与 `Done/Total` 分开命名，避免与"已完成的文件数"混在一起。

界面侧：

* 收到 `item` 就把"计算中"打在那一行上（**比"游标指向下一条等待中的"更准**：真正决定顺序的是目标机），
  百分比归零，计时起点挪到这一刻；同时把其它行还挂着的"计算中"摘掉 —— 一次只算一个文件，
  两行同时跳一个计时会让人以为在并行算。
* 收到 `bytes` 只贴到"正在读"的那一行，且**路径要对得上**：stdout 与 stderr 是两条独立的流，
  一行迟到的进度帧完全可能在下一个文件已经开始之后才到，贴错了百分比就会乱跳。
* 状态格里显示 `73% · 已用 1:20`；报不出字节时（`percent` 为 null）只显示 `已用 1:20`。
  算完即清空百分比 —— 它描述的是过程，不是结果。

**两个必须记住的坑（都踩过，且都不报错）**：

1. **行对象要存响应式代理，不能存原始对象。** `hashRows` 是 `ref([])`，往里 push 之后读回来的
   是 `reactive` 代理；如果另用一张 `Map<path, row>` 存**原始对象**（`hashIndex` 就是干这个的），
   那么"按路径改那一行"（结果帧、进度帧、百分比）改的是原始对象 —— **不触发重渲染**。
   表现是：服务端明明算完、库里明明有摘要，界面却一片空白，控制台也没有任何报错。
   所以 `indexHashRow` 统一"push 之后再从 `hashRows` 里读一次，把读回来的那个存进索引"。
2. **处理帧时的异常不能被当成"解析失败"吞掉。** `streamNDJSON` 原先把 `JSON.parse` 与
   `onEvent` 包在同一个 `try` 里、`catch` 里静默忽略 —— 于是调用方的逻辑错误会让那一帧凭空消失，
   而且是全静默的。现在拆成 `dispatchFrame`：解析失败照旧丢弃（不影响后续帧），
   处理失败则 `console.error` 记一条，好让这种"界面空白但没有线索"的情况可查。

### 9.5 中止

哈希要读完整的数据，几十 GB 的文件可能跑很久；而"没有中止"就意味着用户只能干等，
此前每次部署重启面板都会打断正在跑的那一趟（记录会落成"已中断"，但活儿白干了）。

* 「开始计算 / 重新计算」在计算中**变成「中止计算」**（`type="warning"`）。
  关闭弹窗（Esc、点遮罩）仍然被驳回，并提示"要停下来请点「中止计算」" ——
  中止是明确的意图，Esc 更可能是误触，不该顺手把一趟跑了很久的任务废掉。
* 中止 = `AbortController.abort()`，走的是 `streamNDJSON` 已有的 `signal` 参数。
  远端连接一断，`execOnHostStream` 会在 `ctx.Done()` 上终止目标机的那条命令，
  不会留下一个还在读盘的进程。
* 中止**不是失败**：`collectHashes` 返回 `aborted`，界面只弹一句"已中止计算，
  已经算完的摘要保留"，不弹红色错误；已经收到的结果照旧留在表格与任务记录里。
* 窗口被关掉（卸载）时也一并 abort —— 窗口都没了，再让它读下去只是白白占着目标机的盘。

### 9.6 验证

* `TestParseHashItem`：路径含空格、纯数字校验、`PANELSSH_HASH_PROGRESS` 之类的错行不被误认。
* `TestParseHashBytes`：空字段不被当成 0（会把进度条从 80% 拽回 0）、越界钳到 100%、
  分母为 0 的行整行丢弃。
* `TestHashScriptReportsItemsAndKeeepsDigest`：用**真的 sh 与真的 md5sum** 跑一遍生成的脚本 ——
  一个大文件（超过门槛）必须报一次 item 且字节数与实际一致，两个文件的摘要必须与面板自己算的
  **逐字节一致**。这条测试是这套改动的底线：包装脚本一旦动到读取或输出格式，
  表现分别是"进度不动"或"结果少几条"，都不会报错。
* 面板侧的字节进度由既有 `hashViaPanel` 用例覆盖（若将来补上），至少保证 `hashOneFile` 的签名变化
  不影响结果。
